# Design Strategy — ツールを開く前に勝負は終わっている

## Core Philosophy

AIで「実行」（コード・画面・試作品・文章）のコストは激減した。しかし「誰のために何を
作るか」を**判断するコスト**は1円も下がっていない。むしろ、誰でも作れるようになったぶん、
判断できる人とできない人の差が露骨に見えるようになった。

プロのデザイナーがFigmaなどのツールを開いている時間は全体の10-15%以下。残り85-90%は
思考・戦略・言語化。ツールを開くのは答えが固まってから。

**設計の能力とは「形にできるか」ではなく「何を作るかを決める判断の質」である。**

この戦略フェーズが曖昧なまま作り始めると、途中で何を作っているのか分からなくなり、
全部やり直しになるか、誰にも刺さらないものが出来上がる。逆にここが定義できていれば、
どの機能を入れるか・何を削るか・何を優先するか、後の全判断に軸が通る。

## When NOT to run this skill

- バグ修正・リファクタ・既存機能の小改修（作るものが既に定義済み）
- 既に有効な design-strategy.md / PRD / PR-FAQ が存在し、3つの問いに答えがある場合
  → 既存文書を Read して軸として使い、実装へ進む

## Workflow

### Step 0: 既存の答えの確認

プロジェクト内に `design-strategy.md`, `PRD*`, `*pr-faq*` 等が無いか Glob で確認する。
あれば読み、3つの問い（WHO/GOAL LINE/PRINCIPLES）が答えられているか評価。
全て揃っていればこのスキルをスキップしてよい。欠けている問いだけ以下を実行する。

### Step 1: 誰のために作るのか（WHO + 欲望）

**1-a. ターゲット一文を書く。** フォーマット:

> 「`<具体的なグループ>` が `<具体的な反応・行動・言葉>` をしてくれたら成功」

例:「日本で働く20-50代で、キャリアを考え直したい・グローバルで戦いたいプロフェッショナルが、
『この情報は他で得られない』と感じて毎週戻ってきてくれたら成功」

解像度を極限まで高める。その人がどんな言葉を言い、どんな行動を取ったら成功なのかまで詰める。

**1-b. アンチパターンガード（最重要）。** ユーザーの回答に以下のシグナルが出たら、
そのまま進めず問い直す:

| Red flag | なぜ最悪か |
|---|---|
| 「みんなのため」「幅広い層に」「できるだけ多くの人に」 | 対象を広げるほど解像度が下がり、誰の何の価値かがぼやける |
| 「あの層もこの層もカバーしたい」 | みんなのためのデザイン＝誰の心にも引っかからないメディオクリティ（凡庸さ） |
| 「嫌われたくない」 | 悪いデザインには直す手がかりがあるが、凡庸なデザインには手がかりすらない。凡庸さは悪いデザインより価値が低い |

問い直しの方向: **尖らせる**。みんなに好かれなくても、嫌われてもいい。ある層から熱烈に
支持される定義を目指す。尖るほど強い感情的反応＝ファンが生まれる。

参考例（ユーザーに提示してよい）: Teenage Engineering OP-1 — 約30万円のシンセ。
チュートリアルなし・初心者お断り・ユーザビリティ原則を全無視。だが「制約の中で音楽を作る」
という特定ユーザーの特定の欲望を妥協なく直撃し、プロの熱狂的ファンを獲得した。
使いやすさ・分かりやすさ・安さを**捨てた**から刺さった。

**1-c. 欲望チェーン（芋づる式）。**「誰のために」だけでは浅い。設計＝心理学。
幸福とは欲望が満たされた時に発生する。表面的なニーズから根っこの欲望まで辿る:

```
表面のニーズ:「仕事を効率化したい」
  → なぜ? 時間・精神的余裕が欲しい
    → その余裕で何を成し遂げたい?
      → それを成し遂げると何が満たされる?（承認? 安心? 知的好奇心? 社会的成功?）
        → ★ これが root desire。製品はこの欲望への応答として設計する
```

AskUserQuestion で2-3往復の壁打ちを行い、root desire を特定する。
AIによるブレスト・壁打ちはこの段階で有効。ただし「何が本当に刺さるか」の最終判断は
ユーザー（人間）に委ねる — ここはセンスの領域であり、AIが代行できると偽らない。

**Step 1 完了条件**: ターゲット一文 + root desire が1-2行で書けている。

### Step 2: どこまでやれば価値が生まれるのか（ゴールライン）

ゴールラインが未定義だと作る範囲が無限に広がり（「この機能も」「あれも必要かも」）、
永遠にリリースできない。**Amazon PR/FAQ プロセス**で先にゴールを定義する。

**2-a. 仮想プレスリリースを書く。** まだ存在しない製品の「完成後の発表文」を
コンセプト段階で書く。通常PRは最後に書くものだが、最初に書くことで技術・予算・期間の
制約から切り離され、**顧客にとって何が価値かだけ**に集中できる。

構成（200-400字程度）:
1. 見出し: 何が出たか
2. 誰のために作ったか（Step 1のターゲット）
3. 使うと顧客の生活/仕事がどう変わるか（感情の変化まで書く）

例文の型:「本日◯◯を提供開始します。`<ターゲットの痛み>` と感じている方のために
作りました。使い始めると `<具体的な感情変化: 「1日の終わりに今日はうまくいったと
思える瞬間が増える」>`」

**2-b. FAQ を書く。** 2系統:
- **顧客向けFAQ**: これどうやって使う? どう始める? 何が変わる? どんな価値がある?
- **社内向けFAQ**: 財務的に成り立つか? どうサポートするか? 法的な問題はないか?

全部、製品ができる前に答えを書く。答えられない質問＝設計の穴。

**2-c. 競合リサーチ（順番厳守: PR/FAQ の後）。** 先に価値を定義してから競合を見る。
逆順にすると競合の真似から発想してしまう。WebSearch で競合を調べ、品質ラインを校正:

- **過密市場**（例: SaaSプロジェクト管理 — Asana/Notion/Linearと戦う）
  → 「使える」だけでは全く足りない。要求ラインは自動的に上がる
- **競合不在領域** → 存在自体が価値。求められる質は低くてよい。唯一性が価値になる

「どこまでやれば十分か」は市場と競争相手で決まる**相対的なライン**。
社内政治で決まったゴールではなく、本当に意味のあるゴールラインを設定する。

**Step 2 完了条件**: 仮想PR + FAQ + 「この市場ではこの質まで磨けば価値」の一文。

### Step 3: デザインプリンシプル（何を優先するか）

製品を作っているとあらゆる方向から横やりが入る（PM「この機能追加して」/ 上司「もっと
シンプルに」/ エンジニア「実装コスト高い」/ マーケ「このメッセージ入れて」）。
全部聞いたら何もかも中途半端になる。プリンシプルはそのために存在する。

**3-5個の原則を、必ずトレードオフ形式で書く:**

| 形式 | 判定 |
|---|---|
| 「ユーザーを第一に大切にします」 | ❌ ただのスローガン。意思決定に使えない |
| 「速さ vs 機能の豊富さ → 速さを優先する」 | ✅ プリンシプル。横やりへの答えが出せる |
| 「美しさ vs 多少の学習コスト → 美しさを優先。チュートリアルで補う」 | ✅ |

良いプリンシプルの判定基準は1つ: **意思決定の場で実際に使えるか**。
迷った時・横やりが入った時に「私たちのプリンシプルはこれです。だからこの方向には
行けない」と答えが出せること。

**Step 3 完了条件**: トレードオフ形式のプリンシプル3-5個。

### Step 4: 成果物の保存

`design-strategy.md` をプロジェクトの適切な場所（`docs/` があればそこ、なければルート）に保存:

```markdown
# Design Strategy: <プロジェクト名>
日付 / 作成者

## 1. 誰のために（WHO + 欲望）
- ターゲット一文: ...
- Root desire: ...
- 捨てるもの（このターゲットのために犠牲にするもの）: ...

## 2. ゴールライン
### 仮想プレスリリース
...
### FAQ（顧客向け / 社内向け）
...
### 競合と品質ライン
...

## 3. デザインプリンシプル
1. X vs Y → X を優先（理由）
2. ...

## 完成の定義
この3つに照らして判断できない機能・要素は入れない。
```

以降の実装・デザイン作業では、機能追加・削除・優先順位の判断のたびにこの文書を軸にする。

## 完成条件（このスキルの出口）

3つの問い — **誰のために / どこまでやれば価値か / 何を優先するか** — に
ユーザー自身の言葉で答えが書けて初めて、ツールを開く・実装を始める資格ができる。
この3つが固まっていれば、作りながら迷わなくなる。

## Red Flags 一覧（作業中も常時監視）

これらが出たら戦略に立ち戻る:
- 「みんなに使ってほしい」「幅広く」→ Step 1 へ戻る
- 「機能は多いほどいい」「念のためこれも入れよう」→ Step 3 のプリンシプルで判定
- 「とりあえず作ってから考える」→ Step 2 のゴールラインを先に
- 「競合がやってるからうちも」→ PR/FAQ で定義した価値に照らす
- 作業途中で「あれ、何を作ってるんだっけ」→ design-strategy.md を Read し直す
